The experiment

The same Flask checkout as the static benchmark, but the test suite grows while hh keeps its measurement history.

Starting from 494 passing Flask tests, six events add a total of 23 synthetic pytest tests. Their sleep durations are seeded random integers from 100–250 ms, adding 3.845 s of scheduled sleep by the end. They are deliberately artificial workload, not new Flask behavior or realistic production tests.

Each of 30 iterations runs hh once and runs the real pytest command separately at each guess G = 1, 2, 5, 10, 20 and 30 s. A naive timeout kills and restarts from zero at double the guess, up to four attempts. Arms see the same growing tree; naive order is seeded and shuffled, while hh alternates between first and last. The store is reset before iteration 1 and retained thereafter. Each comparison uses the actual hh process wall from that same iteration, including planning and discovery, not a static median.

Does hh support a changing suite?
  • Discovery: pytest manifests are cached using a filesystem fingerprint; new or deleted .py files change it, prompting rediscovery. This experiment adds new files; a separate ledger check verifies every generated test ID passed on every subsequent iteration.
  • Estimation: previously seen IDs use their measurements; unseen IDs fall back to file or suite averages until they have their own observations. A new, unexpectedly slow test can therefore be underestimated on its first run. coverage is estimated duration mass, not the fraction of test IDs; confidence is calculated after execution, and read 1.0 at the additions despite unmeasured tests in the plan.
  • Important cache limitation: the fingerprint uses path, file size and integer-second mtime, not file content. A same-size edit in the same second (or one preserving the mtime) may reuse a stale manifest. A separate controlled one-test check renaming test_one to test_two while preserving size and mtime returned shard_failed, rather than running the new test. Invalidation also does not include pytest configuration files or HH_PYTEST_ARGS. Remove that store's .hh/manifest-pytest.json to force rediscovery after such changes; do not assume every edit is detected.
  • Scope: this benchmark tests additions, not arbitrary edits, deletions, config changes or test identity collisions. It is evidence for this scenario, not proof that all suite changes are supported.

How to read this honestly
  • Not production changes. Added tests only sleep; runtime increase is intentionally controlled and is not evidence about real new Flask features or representative test durations.
  • One machine and one suite. Runs are sequential, order varies but is not fully randomized; 30 calls share hh's progressively updated history and OS caches. Data are not independent cold trials. A brief separate cache-edge investigation ran concurrently near the beginning and may affect early timings.
  • Fair clock, different invocation. Both arms run the same intended tests and disable pytest's cache provider. Naive uses pytest tests; hh drives node IDs and writes a ledger. The comparison uses total hh process wall, not just the smaller runner-only wall_s.
  • Cold start included. Iteration 1 is a record pass, with no measured prediction. The hh call at each iteration is compared against six separately executed naive guesses; summing differences repeats that cost six times.
  • Verified results. The script checks naive pytest's passed count and hh's distinct ledger outcomes, not merely hh's status. No result means no saving is claimed. Whether a timeout exercises resume can be seen in the raw results.
